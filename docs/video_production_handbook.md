# 代码做视频：方法库 · 剪辑经验 · 流程优化

> 来源：本项目的三轮实践（v1 纯程序化 → v3 85 秒成片 → v4 三类素材混剪），加上对公众号文章《只需一句话，用 TRAE 帮你做动画视频》里 4 个可复用资产的调研。
> 目的：下次做视频时不用重新试错，直接按「需求 → 方法」查表。

## 0. 一页速查：什么需求选什么方法

| 需求 | 首选 | 备选 | 不推荐 |
| --- | --- | --- | --- |
| 逐帧精确卡点、可复现 | 程序化渲染 / HTML + Playwright 截帧 | 开源 MV 项目改代码 | 纯 AI 视频生成 |
| 真实人物、实拍感镜头 | AI 图 + Ken Burns，或图生视频 | 传统混剪 | 纯 PIL 几何绘制 |
| 快速出成片、可以接受模板化 | 复刻开源 MV 项目 | 一站式 MV Skill | 从零写渲染器 |
| 现成网页 → 演示视频 | hyperframes / Playwright 截帧 | 录屏 | — |
| 素材已就绪、只做包装 | 剪映 / PR / DaVinci | ffmpeg 脚本 | 重新渲染 |
| 版权敏感（不能商用他人音乐） | 程序化配乐 + 原创画面 | 授权素材库 | 原曲 + 原作截图 |

**核心判断**：可控性、成本、出片速度三者不可能同时最优。先确定「卡点精度」是不是刚需，再决定路线。

## 1. 项目复盘：三轮实践各踩了什么坑

| 版本 | 时长 / 音乐 | 画面 | 主要问题 | 得到的结论 |
| --- | --- | --- | --- | --- |
| v1 | 24 秒 / 自写 120 BPM 程序化配乐 | 纯代码：电磁炮、充能、发射、冲击波、HUD | 音色单薄、叙事容量小 | 程序化完全可控，但"从零造世界"成本极高 |
| v3 | 85 秒 / 外部音轨（143 BPM 剪辑版） | 22 个镜头，12 发炮击，4 种转场，卡拉 OK 歌词层 | 全程围着同一门炮，视觉疲劳 | 卡点与歌词层已成熟，缺的是**素材多样性** |
| v4 | 85 秒 / 同上 | 39 个镜头：22 张 AI 插画 + 11 段网页特效（10 个页面）+ 6 发炮击 | 重渲成本高、局部文案错误要全段重来 | 混剪结构 + 确定性网页渲染是正确方向，**流程要工程化** |

### v4 的实际配比与耗时（可作为排期参考）

- 总帧数 2558 帧（1920×1080 / 30fps / 85.27 秒）
- 22 张 AI 插画镜头 + 16 张素材图；11 段网页镜头（10 个页面，636 帧截图，214 MB）
- 全量渲染：4 进程约 10 分钟（单帧约 1 秒，瓶颈在 PIL 后处理与磁盘 IO）
- 只重渲插画段（1369 帧）约 6 分钟——**改一个 HUD 文案就要 6 分钟，这是最该被优化的点**
- 成片：129–135 MB，约 12.7 Mbps；540p 预览 17 MB

## 2. 方法库（11 种）

每种方法统一按「原理 / 适用 / 优点 / 坑 / 本次结论」记录。

### M1 纯程序化逐帧渲染（Pillow + numpy + scipy）

**原理**：每一帧由一个纯函数 `render_frame(i)` 计算，`i` 是帧号；所有几何、光效、粒子都是代码。
**适用**：抽象图形、UI 风格、需要精确卡点的特效片、版权敏感项目。
**优点**：100% 可控、可复现、无素材版权问题；改参数即可换风格；能和节拍表严格对齐。
**坑**：
- 单帧 CPU 成本高，复杂后处理（bloom、blur、色差）尤其慢；
- 审美上限取决于几何与材质功底，容易做出"PPT 动画"；
- 代码量大，v1 单文件就 40 KB。
**本次结论**：适合做"系统界面 / 遥测 / 炮击"这类几何感强的段落，不适合承担整片叙事。

### M2 程序化配乐（numpy / scipy 合成）

**原理**：振荡器 + 噪声 + 滤波器 + 包络，全部用 numpy 合成，导出 WAV。
**适用**：占位音轨、无版权要求的演示、需要"画面与节拍同源"的项目。
**优点**：节拍事件表可以和画面共用一份配置；零版权风险；改 BPM 即可全局变速。
**坑**：音色单调、混音粗糙；做 3 分钟以上会明显重复；观众对"电子 loop"的容忍度低。
**本次结论**：24 秒短片够用；正式作品建议用现成音轨，再把事件表对齐到它。

### M3 外部音轨 + ASR 歌词打轴（Whisper + 人工校正）

**原理**：对剪辑版音轨跑 ASR，得到粗时间轴，人工逐句校正，输出 `lyrics.json`（`t/end/jp/cn/hit`）。
**适用**：网上 LRC 对不上剪辑版、或歌词被重新编排的 MV。
**优点**：时间轴是整条流水线的基础，一次做对后面全受益；可标记"金句"用于视觉强调。
**坑**：
- ASR 断句按语义走，不等于演唱换气点，必须人工听；
- 剪辑版可能删句/并句，LRC 直接套会整体漂移；
- 需要额外准备中文翻译行。
**本次结论**：22 句歌词的时间表是 v3/v4 最有价值的资产之一，务必版本化管理。

### M4 AI 文生图 + Ken Burns 运镜

**原理**：生成 16:9（或更大）插画，运行时裁切 + 推拉摇移 + 统一调色。
**适用**：二次元/概念场景、无法实拍的镜头、需要高质感的静态叙事。
**优点**：质感远高于手绘几何；出图快；同一套 prompt 可批量产出。
**坑**：
- 右下角生成水印（裁切或用更大画幅再裁）；
- 手部、文字、多人构图容易崩；
- 同一角色跨图不一致（发型、制服细节漂移）；
- 风格漂移，需要统一调色把 16 张图"焊"成一部片子。
**关键参数**：裁切后约 2304×1296；zoom 1.0–1.2 做缓慢推拉；单镜头 2–4 秒；统一 grade（青蓝暗部 + 洋红高光）。
**本次结论**：**性价比最高的"世界构建"手段**，但必须配统一调色和克制的运镜，否则像幻灯片。

### M5 HTML/CSS/JS + Playwright 确定性截帧 ★ 本次最大收获

**原理**：每个特效页是一个 1920×1080 的网页，暴露 `window.__seek(t)`；渲染器用 `?t=` 参数打开页面，等待字体/资源就绪后截图；页面内所有动画只依赖传入的 `t`，**不用 requestAnimationFrame**。
**适用**：数据面板、终端/雷达、漫画分镜、海报排版、故障特效——一切"网页比 Python 好画"的画面。
**优点**：
- 表现力碾压 PIL：CSS 渐变、混合模式、SVG、字体排版开箱即用；
- 改样式只改 CSS，重截单页即可；
- 完全确定性：同一 `t` 永远同一帧，可与音轨精确对帧；
- 一页可复用多个镜头（换时间区间/换裁切即可）。
**坑**：
- 动画写成 rAF 就会随机漂移，必须改成时间函数；
- 字体必须用系统已安装的 CJK 字体，否则缺字/回退；
- 截图慢（每帧数百毫秒），24fps × 10 页 = 636 帧；
- **不要把整帧读进内存缓存**（1920×1080×3 ≈ 24 MB/帧，几百帧直接爆内存）；
- Playwright 的 Chromium 在大文件 CDN 受限时需要分块下载 + 手动安装系统依赖；
- 网页自带页眉时，全局 HUD 要关闭，否则两套时间码/编号互相打架。
**本次结论**：**值得沉淀成模板**。建议固定一套 `base.css + app.js`（提供 clamp/lerp/smooth/hash/wob/时间码/__boot），新页面只写内容。

### M6 程序化几何 / 伪 3D 特效（电磁炮）

**原理**：3D 点投影到 2D，画轨道、线圈、电弧、弹道、冲击波、爆炸；叠加色差、震动、速度线。
**适用**：机械/科幻主体、需要"重复但每次不同"的爆点。
**优点**：同一套资产可以靠机位/焦距/色调做出多个镜头；冲击帧可控。
**坑**：
- 装饰性轨道环一多就变"抽象画"，观众看不懂在打什么；
- 机位雷同 → 12 发炮击看起来像 1 发重复 12 次；
- 缺少尺度参照，画面会显得"塑料"。
**本次结论**：6 发、6 种取景（远景仰拍 / 炮口特写 / 荷兰角 / 逆光 / 长焦 / 低角度）刚好；加遥测数字、准星、目标编号能显著提升"真实感"。装饰环透明度要压到很低（约 0.016），zoom ≥1.45 时不画。

### M7 图生视频 / 文生视频大模型（Seedance、Kling、Wan 等）

**原理**：给一张图或一段 prompt，模型直接生成 5–10 秒动态镜头。
**适用**：氛围过场、空镜、预告片式镜头、需要真实运动而无法用 Ken Burns 的场景。
**优点**：运动自然、光影真实、单镜头质感高。
**坑**：
- 单次时长有限，镜头之间不连续，角色/服装一致性差；
- 文字、口型、精确动作不可控，**无法做逐帧卡点**；
- 生成排队与成本，失败重试不可控；
- 输出分辨率/帧率需要统一转码后才能混剪。
**本次结论**：只适合当"实拍感补充镜头"，不要指望它承担叙事与卡点；若要混剪，先把所有片段统一到 1920×1080/30fps/同一调色。

### M8 复刻开源 MV 项目（world-execute-me-dsh-pv / pdoom-video）

**原理**：项目本身就是"代码生成 PV"，克隆后放歌、跑构建。
**适用**：想快速拿到高质量成片、或学习别人的同步与视觉做法。
**优点**：完成度高；代码即教程；pdoom 用 Bun + Chrome 渲染，思路与 M5 相通。
**坑**：
- 为某一首歌写死，换歌要改代码（时间轴、分镜、歌词都硬编码）；
- 环境重（Bun / Chrome / FFmpeg libx264）；字体跨平台差异会导致排版偏移；
- 直接复刻 = 同款，二次创作仍需大量改造。
**命令备忘**：

```bash
# world-execute-me-dsh-pv
python build.py all          # 1280×720
python build.py all --4k

# pdoom-video（在 app/ 下）
bun scripts/render.ts video --samples auto --shutter 0.2 --out ../out/pdoom.mp4
```

### M9 一站式 MV Skill（ai-music-video）

**原理**：`song.mp3 + lyrics.txt + 风格提示词`，由 Skill 编排图像/视频/音乐模型与歌词对齐，最后渲染。
**适用**：任意歌曲的 MV、歌词视频、卡拉 OK 字幕；不想从零搭流水线。
**优点**：覆盖风格选择、歌词与节拍对齐、分镜、口型检查、渲染全流程；可调用 MJ/SD/Flux、Seedance/Kling/Wan、Suno。
**坑**：风格与分镜质量高度依赖提示词；外部模型额度与排队；一致性仍需人工把关；成品可控性低于自建渲染。
**提示词模板**：

> 用 ai-music-video Skill，把 input 目录下的 song.mp3 和 lyrics.txt 做成逐词高亮的歌词视频。风格：赛博、热血、二次元。用纯代码动画实现，1920×1080，30 fps，保留原音频。

### M10 hyperframes（网页 → 视频）

**原理**：不录屏，直接以页面 DOM/CSS/交互状态为素材，按场景编排渲染成视频。
**适用**：产品功能演示、宣传短片。
**优点**：真实界面、可交互状态、默认 1920×1080/30fps；不乱加配音字幕。
**坑**：不适合歌曲类 MV（没有音乐节拍与歌词层概念）；依赖真实页面素材。
**本次结论**：和我们的 M5 是同一类思路，差别在于它面向产品演示、我们面向卡点 MV。

### M11 传统剪辑软件混剪（剪映 / PR / DaVinci）

**原理**：素材导入时间线，手动或按节拍标记剪切，调色、音效、字幕。
**适用**：素材（动画片段、实拍、AI 视频）已经就绪，只需要包装。
**优点**：最快出片；调色/降噪/音效成熟；所见即所得。
**坑**：逐帧卡点靠手感，难以精确到帧；版本管理与批量复用差；改一个元素要手动同步多处；素材版权风险最高。
**本次结论**：适合最终包装或应急交付；想要"可复现、可批量"，仍然要回到代码流水线。

## 3. 剪辑经验（可直接套用的规则）

### 3.1 节奏

- 常规镜头 1.5–3 秒；副歌 0.7–1.5 秒；桥段可放 4–6 秒做"呼吸"。
- 每 8 小节设一个燃点，结构是「蓄力（低饱和、慢推、长镜头）→ 释放（高对比、碎切、闪白）」。
- 强拍切镜，弱拍只做运动（推拉/漂移），不要把切点平均撒在时间线上。
- 85 秒片子的镜头数：20–40 个比较舒服；v4 用了 39 个，平均 2.2 秒。

### 3.2 转场

- 5 种足够：flash（白闪过曝）、whip（水平拖影）、punch（瞬推+震动）、glitch（错位+色差）、fade（首尾专用）。
- 同一种转场至少隔 3 个镜头再用；flash 只留给最大爆点，用多了会廉价。
- 转场长度 0.25–0.35 秒；fade 只放片头/片尾，中段用 fade 会泄气。

### 3.3 混剪配比

- 三类素材建议 5 : 4 : 1（插画 : 网页/界面 : 程序化特效），单一类型连续不超过 4 个镜头。
- 素材切换要有"叙事理由"（歌词、场景、情绪），不要为了换而换。

### 3.4 歌词与字幕

- 歌词层是**固定层**，不参与镜头缩放/旋转/抖动，永远清晰。
- 逐字高亮，未唱部分压暗（约 30% 亮度）；句长自适应字号（≤16 字用 64px，≤26 字 54px，更长 46px）。
- 中文副行 30px，别抢日文主行；底部加 782–974px 的羽化暗带，保证亮背景可读。
- 副歌金句打 ★ HIT LINE，但整片不超过 5–6 处。
- 网页自带页眉时关闭全局 HUD；亮色页面（如漫画墙）必须靠暗带救歌词。

### 3.5 构图与标题

- 人物在右就把标题放左（反之亦然），标题中心离主体至少 200px。
- 片头标题整体左侧加椭圆暗化（中心约 540,430，强度 0.5），可读性提升非常明显。
- 片尾 3–4 秒：标题 + 曲名/作者 + 规格 + 版权行，信息一次给全。
- 画面右下角的类型标签要准确：AI 插画写 "ANIME PLATE / AI PAINT"，不要写 "LIVE ACTION"。

### 3.6 色彩统一

- 所有素材走同一套 grade：青蓝暗部 + 洋红高光 + halation + 轻颗粒。
- AI 图与网页截图的对比度/饱和度差异很大，统一调色是"混剪不违和"的关键。
- 每 10–15 秒安排一次色彩反差（夕阳、白纸漫画、绿色监控），但单段不超过 4 秒。

### 3.7 真实感来自"信息噪音"

- 加时间码、CUT 编号、遥测数值、日志流、目标编号、监控时间戳，画面立刻"像真的系统"。
- 但信息层级要克制：主标题 > 数据 > 装饰线，别让 HUD 抢戏。

## 4. 流程与优化

### 4.1 标准流水线（8 步）

1. **定音频**：确定音轨与 BPM（本次 143 BPM），锁定不可替换。
2. **事件表**：`events.json`（BPM、拍点、发射/爆点时间）+ `lyrics.json`（逐句时间、日中文本、金句标记）。
3. **分镜表**：每个镜头一行——类型（image/web/cannon）、起止时间、素材、机位（zoom/cx/cy/rot）、转场。
4. **素材生产**：AI 图批量生成/挑图/裁水印；网页逐页开发；程序化特效调参。
5. **Animatic**：480p / 12fps 低清预览，先把剪辑节奏定死，再谈画质。
6. **正式渲染**：分段并行；UI/歌词层最后合成。
7. **合成**：ffmpeg 编码 + 音频 + faststart；生成 540p 预览。
8. **QA 与交付**：ffprobe 校验、抽帧检查、黑帧/水印/歌词可读性、上传归档。

### 4.2 本次暴露的瓶颈

| 问题 | 现象 | 代价 |
| --- | --- | --- |
| 全量重渲 | 改一个 HUD 标签，需重渲 1369 帧 | 约 6 分钟/次 |
| 渲染与 UI 耦合 | 歌词/标题改动也要动画面 | 无法快速迭代文案 |
| 中间帧落盘 | 2558 张 JPEG 约 1.8 GB | 磁盘 IO 成为瓶颈 |
| 网页截帧缓存 | 曾把整帧读进内存 | 有 OOM 风险 |
| 素材无清单 | 16 张图靠文件名管理 | 换图/回滚容易乱 |
| 无自动 QA | 靠肉眼抽帧 | 漏检黑帧、重复帧、水印 |

### 4.3 优化清单（按收益排序）

1. **时间轴单一配置**：用一份 `timeline.json` 同时驱动渲染、字幕、文档与 QA；禁止在代码里散落时间常量。
2. **分层渲染 + 静态层缓存**：背景、暗带、HUD 底图只算一次；UI 与画面分开合成。
3. **字幕/标题后合成**：把歌词层输出成 PNG 序列或 ASS 字幕，用 ffmpeg 叠加；改字零重渲。
4. **增量渲染**：给每个镜头算参数 hash，写入 manifest；只重渲 hash 变化的段落（本次若做了，6 分钟可变 10 秒）。
5. **中间帧直通 ffmpeg**：Python 生成 RGB 帧后 pipe 给 ffmpeg（`-f rawvideo`），省掉 1.8 GB 落盘；或只在需要断点续渲时落盘。
6. **代理渲染**：animatic 用 480p/12fps；网页页可 12fps 捕获后光流补到 30fps，成本减半。
7. **网页模板化**：固定 `base.css + app.js`（工具函数 + `__boot` + `?t=` 解析），新页面只写内容；截图脚本支持单页重截。
8. **自动 QA 脚本**：ffprobe 校验分辨率/帧率/时长/音频；`blackdetect` 查黑帧；抽 12 帧拼 contact sheet；检查首尾各 3 秒。
9. **素材 manifest**：记录每张图的 prompt、seed、裁切框、使用镜头；网页记录 commit。
10. **并行度调优**：4–8 进程按 CPU 核数；JPEG q94 中间帧比 PNG 快 3–5 倍。

### 6.2 Playwright 逐帧截取（核心逻辑）

```python
from playwright.sync_api import sync_playwright

W, H, FPS = 1920, 1080, 24
PAGE = "http://localhost:8000/pages/01_radar.html"

with sync_playwright() as pw:
    b = pw.chromium.launch()
    pg = b.new_page(viewport={"width": W, "height": H}, device_scale_factor=1)
    pg.goto(PAGE, wait_until="networkidle")
    pg.wait_for_timeout(500)              # 等字体/图片
    for i in range(frames):
        pg.goto(f"{PAGE}?t={i / FPS}", wait_until="load")
        pg.wait_for_timeout(60)
        pg.screenshot(path=f"assets/web/radar/f_{i:04d}.jpg",
                      type="jpeg", quality=92)
    b.close()
```

> 注意：逐帧 `goto?t=` 比在页面里 `evaluate(__seek)` 更稳（不会残留上一帧状态），但更慢；页面简单时可直接 `evaluate` 后截图。
